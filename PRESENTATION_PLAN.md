# План презентации: ИИ для инженеров нагрузочного тестирования

**Тема:** Внедрение ИИ в работу инженеров НТ — два инструмента для разных сценариев
**Аудитория:** смешанная (инженеры НТ/QA + руководство)
**Формат:** слайд-дек (~18–20 слайдов), ориентировочно 25–30 минут + демо
**Главная идея:** мы внедряем ИИ в нагрузочное тестирование не «одной кнопкой», а как набор решений — разные инструменты закрывают разные потребности, чтобы вариант нашёлся для каждого инженера и любой стадии зрелости команды.

---

## Сквозной нарратив

1. У инженеров НТ много рутины и высокий порог входа — ИИ может это снять.
2. Мы не делаем один универсальный инструмент: команды и проекты разные.
3. Поэтому два дополняющих решения:
   - **GigaMeter** — ИИ-ассистент *внутри JMeter*: помогает там, где команда уже работает сегодня.
   - **Gatling-AI Workflow** — ИИ-агент, который *строит и мигрирует* тесты на Gatling-as-code: для модернизации и перехода на код.
4. Вместе они покрывают спектр: «улучшить здесь и сейчас» ↔ «перейти к тестам-как-код».
5. Что дальше: дорожная карта, риски, как попробовать.

**На слайде:** название, авторы, дата.

> Заметки: одна фраза-крючок — «Мы хотим, чтобы каждый инженер НТ получил ИИ-помощника под свою задачу, а не один инструмент для всех».

## Слайд 2 — Боли инженера НТ (зачем вообще ИИ)

**Тезисы:**

- Высокий порог входа: Groovy/JSR223, Scala/Java для Gatling, нюансы инструментов.
- Много рутины: именование элементов, обвязка транзакций, разбор чужих скриптов.
- Легаси без документации: что вообще тестирует этот `.jmx`?
- Долгий путь «требование → запускаемый тест» — дни вместо часов.
- Миграция между инструментами (JMeter → Gatling) — дорогая и ручная.

> Заметки: для руководства это = время, стоимость, риск ошибок и зависимость от «носителей знания». Поставить вопрос, на который ответят следующие слайды.

---

## Слайд 3 — Наш подход: не один инструмент, а набор решений

**Тезисы:**

- Команды на разной стадии: кто-то живёт в JMeter, кто-то переходит на Gatling-as-code.
- Один универсальный инструмент не закроет оба мира.
- Принцип: дать ИИ-помощника под каждый сценарий, встроить в текущий рабочий процесс.

**Визуал:** спектр из двух полюсов:
`Улучшить то, что есть (JMeter)` ←———→ `Модернизировать в код (Gatling)`
с двумя инструментами на своих местах.

> Заметки: это ключевой слайд нарратива — «решения для всех опций».

# Часть I. GigaMeter — ИИ внутри JMeter

## Слайд 5 — GigaMeter: CLI-first (что это)

**Тезисы:**

- Плагин для Apache JMeter с панелью ИИ-чата; версия **v0.5.0-beta, CLI-first**.
- **Движок по умолчанию — локальный GigaCode CLI** (или Qwen Code), без API-ключей. Тот же корпоративный движок, что и в Gatling-AI Workflow → единая экосистема.
- Облачные провайдеры (OpenAI/GigaChat/DeepSeek) скрыты за флагом `gigameter.providers.cloud.enabled` — архитектура провайдер-агностичная.
- Транспорт: Windows-safe запуск (cmd /c), таймаут, раздельный дренаж stdout/stderr. UX: стриминг (stream-json), кнопка Stop, сессии `--resume`, выбор модели.
- Совместимость: JMeter 5.5 / 5.6.2, Java 17.

> Заметки: главный акцент — приватность (локальный движок, данные не уходят в облако) и единый движок обоих инструментов.

---

## Слайд 6 — GigaMeter: агент правит план (jmeter-ops)

**Тезисы (главное в v0.5):**

- Плагин подмешивает в промпт текущее дерево (каждый элемент с `#id`) + протокол операций.
- Агент отвечает блоком ` ```jmeter-ops ` с JSON-операциями: `add_element`, `remove_element`, `set_property`, `replace_subtree`, `new_test_plan`, `get_element`.
- Цикл применения: **preview диффа → confirm → apply на EDT → undo (`@rollback` / кнопка)**.
- Надёжность: JSON-repair, толерантный экстрактор, дельты поверх обрезанного ответа; collection-свойства (body/params/headers/assertions). Без `--yolo` — file-write инструменты CLI отключены.

> Заметки: это и есть «интерактивная интеграция», которая раньше была дизайном — теперь реализована.

---

## Слайд 7 — GigaMeter: команды как Skills + BlazeMeter

**Тезисы:**

- Промпты команд вынесены в редактируемые скиллы `~/.gigameter/skills/*.md` (plan, lint, optimize) — правятся без пересборки.
- Curated-набор: `@plan` (генерация/`analyze`), `@lint` (единый стандарт имён), `@optimize`, `@rollback`.
- Поддержка элементов **BlazeMeter / jmeter-plugins**: Concurrency / Stepping / Ultimate Thread Group, Throughput Shaping Timer, Dummy + расписания нагрузки (`utg.schedule` / `tst.schedule`).

**Демо (4–5 минут):** `@plan` логин→заказы→создание заказа → preview → apply → `@rollback`; `@lint` на хаотичных именах; `@plan analyze` на готовом `.jmx`.

> Заметки: подчеркнуть безопасность — preview и откат перед изменением дерева; локальный движок.

---

## Слайд 8 — GigaMeter: ценность и ограничения (честно)

**Ценность:**

- Снижает порог входа в JSR223 и рутину именования/обвязки.
- Работает там, где команда уже есть — не требует смены инструмента.
- Откат и preview снижают риск ошибок.

**Текущие ограничения (для доверия аудитории):**

- План для ИИ сериализуется до 300 элементов — очень большие планы обрезаются.
- `@code` не вставляет ответ обратно в редактор (только чат).
- `@rollback` — один шаг назад, без каскадного undo.
- GigaChat: на части стендов нужна настройка TLS; usage для DeepSeek не реализован.
- Возможны проблемы с кириллицей/тёмными темами в UI.

**Планы:** публикация в Plugins Manager, undo/redo-стек для `@lint`, вставка `@code` в редактор, usage для DeepSeek.

> Заметки: честность про ограничения = доверие, особенно у инженеров. Есть зафиксированный техдолг (промпты, строгий JSON-контракт для @lint, anti-injection в @plan).

# Часть II. Gatling-AI Workflow — ИИ-агент для тестов-как-код

## Слайд 9 — Gatling-AI: что это

**Тезисы:**

- Набор скиллов, команд, хуков и субагентов для **Gigacode** (корпоративный форк Qwen Code, модель qwen3-coder-next).
- Превращает ИИ-агента в инженера НТ на **Gatling OSS** (не Enterprise), генерация на **Java**, сборка **Maven** (Gatling 3.12).
- Решает 5 задач: документация → сценарий; JMeter → Gatling; документирование легаси; сценарий → код; линтеры и самопроверки.
- Методология: Claude Superpowers (brainstorm → plan → execute → debug).

> Заметки: для руководства — это про модернизацию и снятие зависимости от ручной миграции; для инженеров — про код и контроль качества.

---

## Слайд 10 — Gatling-AI: машиночитаемый сценарий как контракт

**Тезисы:**

- Ключевая идея: между «текстом» и «кодом» всегда есть промежуточный артефакт — `scenario.yaml`.
- Единый YAML-контракт описывает: endpoints, методы, заголовки, тело, checks, корреляции, feeders, профиль нагрузки (users/ramp/duration), assertions, протокол шага.
- Никогда не переходим от прозы к коду напрямую — всегда есть ревьюируемый сценарий + отчёт проверки.
- `scenario.yaml` — единственный источник истины: правим сценарий и регенерируем, а не правим Java руками.

**Визуал:** поток артефактов
`Docs/JMeter/диалог → scenario.yaml → passport.md (паспорт) → Java Gatling → quality-gate → тест + отчёты`

> Заметки: это отличает подход от «ИИ накидал код» — есть контракт, который человек ревьюит.

---

## Слайд 10а — Gatling-AI: паспорт скрипта (примеры)

**Тезисы:**

- **Паспорт скрипта (`passport.md`)** — человекочитаемое описание, генерируется из `scenario.yaml`, помечено sha256 источника и «не редактировать вручную».
- Единый шаблон: паспорт (ID, имя скрипта, источник, базовый URL), шаги (читаемые транзакции `01 auth.login - …`), профиль нагрузки, тестовые данные, корреляции, SLA.

**Примеры для показа (реальные, из `examples/scenarios/SHOP/`):**

1. **login-and-search-002** — простой: скрипт `SHOP_LoginAndSearch_002`, 2 шага, extract `csrf`, closed/ramp 10 польз., SLA p95 < 800 ms.
2. **checkout-mix-001** — сложный: 2 популяции (main-checkout closed/stress + background-search open/constant), шаг GraphQL.
3. **legacy-backend-010** — из JMeter (`simple-backend.jmx`): шаги + JSR223-хуки с трассируемостью (`make request id`), тела запросов вынесены в файлы.

> Заметки: показать паспорт как «единый паспорт стенда» — то, что раньше было разрозненной/отсутствующей документацией.

---

## Слайд 11 — Gatling-AI: возможности по фичам

**Тезисы:**

- **Документация → сценарий** (`scenario-from-docs`): из Confluence/файлов/диалога в YAML; на этапе brainstorm агент задаёт уточняющие вопросы, а не угадывает.
- **JMeter → Gatling** (`convert-from-jmeter`): `.jmx` → IR → `scenario.yaml` → Java; для каждого элемента фиксируется диспозиция, неподдерживаемое не теряется молча, а помечается TODO.
- **Документирование легаси** (`document-legacy-jmeter`): человекочитаемая документация по недокументированным `.jmx`.
- **Сценарий → код** (`scenario-to-gatling`): компилируемая Java-симуляция Gatling, сложные профили нагрузки.
- **Отладка по SUT** (план): анализ контрактов API в репозитории тестируемой системы.

> Заметки: подчеркнуть миграцию — это главный «дорогой» сценарий, который ИИ удешевляет.

---

## Слайд 12 — Gatling-AI: контур качества (главное отличие)

**Тезисы:**

- Агент не отдаёт результат «на доверии»: после генерации запускается **quality gate**.
- Детерминированные проверки: JSON-schema сценария, семантические линтеры (`scenario-lint`, `script-style-lint`), компиляция Java, smoke-прогон на детерминированном mock SUT.
- Хуки: авто-линт после правок, запрет «готово» без зелёного гейта, запрет ручной правки сгенерированной Java.
- Независимый **read-only validator-subagent** проверяет артефакты и отчёты до финальной выдачи.
- Отчёты: `quality-gate-report.json` + `.md`. Статусы: `passed` / `passed_with_warnings` / `blocked`.

> Заметки: для руководства — это про управляемость и аудит (никакого «молчаливо неверного» кода). Сильный аргумент про надёжность ИИ-генерации.

## Слайд 14 — Gatling-AI: scope и ограничения (честно)

**В scope сегодня:** HTTP end-to-end (генерация, компиляция, smoke), Java + Maven, миграция JMeter HTTP, контур качества.

**Вне scope / ограничения:**

- Gatling Enterprise не используется.
- Kafka и JDBC: принимаются контрактом и мигрируются, но пока генерируют **TODO-заглушки** (нужен protocol spike).
- GraphQL — поверх HTTP.
- Confluence-публикация, Jenkins/удалённые агенты — задел на будущие фазы.

> Заметки: честно сказать, что это рабочий фундамент + миграция, а не финальный продукт. Это снижает риск завышенных ожиданий.

# Часть III. Вместе

## Слайд 15 — Как два инструмента дополняют друг друга

**Тезисы:**

- **GigaMeter** = «улучшить здесь и сейчас»: команда остаётся в JMeter, ИИ снимает рутину.
- **Gatling-AI** = «перейти к коду»: миграция легаси и генерация тестов-как-код с контролем качества.
- Сценарий перехода: навели порядок в JMeter (`@lint`, `@plan analyze`, документация) → затем мигрировали в Gatling агентом.
- **Общий движок:** Gigacode CLI используется и внутри JMeter (через GigaMeter, режим CLI), и как агент Gatling-AI — единая экосистема и единый вендор.
- Общая нить: ИИ встроен в рабочий процесс инженера, а не «сбоку».

**Визуал:** «дорожка зрелости» — от JMeter+ИИ к Gatling-as-code+ИИ.

> Заметки: это кульминация нарратива «решения для всех опций».

---

## Слайд 16 — Эффект для команды и бизнеса

**Тезисы:**

- Ниже порог входа: меньше зависимость от носителей Groovy/Scala-знаний.
- Быстрее «требование → запускаемый тест» (цель Gatling-AI: ≤ 1 час для типового сценария).
- Дешевле миграция и документирование легаси.
- Выше доверие к ИИ-результату за счёт детерминированного контура качества.
- Гибкость провайдеров ИИ (включая российский GigaChat).

> Заметки: связать с болями со слайда 2 — закрыть круг. Метрики Gatling-AI (компиляция с первого раза ≥90%, автоконвертация ≥80%) — как целевые ориентиры.

## Слайд 17 — Дорожная карта

**Тезисы:**

- **GigaMeter:** Plugins Manager, undo/redo для `@lint`, `@code` → редактор, usage DeepSeek, фиксы UI; техдолг по промптам/контрактам.
- **Gatling-AI:** protocol spike (Kafka/JDBC), Confluence-интеграция, `debug-with-sut`, CI/Jenkins/удалённые агенты.
- Общее: пилот на реальном проекте, сбор обратной связи, метрики внедрения.

**Визуал:** две дорожки на таймлайне (ближний / средний горизонт).

> Заметки: показать, что есть план, а не разовый эксперимент.

## Слайд 18 — Риски и как мы их закрываем

**Тезисы:**

- Качество ИИ-генерации → контур quality gate + валидатор + preview/откат.
- Чувствительные данные в ИИ → не отправлять секреты/PII; секреты через env; GigaChat как локальный вариант.
- Зависимость от внешних API → выбор провайдера, контроль лимитов/стоимости (`@usage`).
- Незрелость отдельных протоколов (Kafka/JDBC) → честные TODO вместо «молчаливо неверного» кода.
- Совместимость платформ (Gigacode/хуки) → spike заложены в план.

> Заметки: для руководства — управляемость рисков; для инженеров — что мы не «продаём магию».
