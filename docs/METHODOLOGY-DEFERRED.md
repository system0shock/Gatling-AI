# Отложенные механизмы МНТ

Статус: вне MVP. Эти механизмы зафиксированы как backlog и не являются
критериями готовности первой версии. Новая реализация и дополнительный
hardening по ним приостановлены.

## Граница MVP

В MVP входят:

- подтверждение состава multi-repo workspace пользователем;
- сбор фактов из Confluence и выбранных репозиториев узкими субагентами;
- сверка противоречий и вопросы только по блокирующим пробелам;
- генерация постоянного `methodology.md` по утверждённому шаблону;
- базовый quality gate;
- показ точного локального diff и явное подтверждение перед сохранением;
- отдельное подтверждение публикации в заранее выбранную страницу Confluence;
- три обязательных отказа публикации: нет подтверждения, изменилась локальная
  МНТ, изменилась версия страницы Confluence.

При актуализации MVP повторно собирает все подтверждённые источники. Это
предсказуемо и достаточно для проверки полезности процесса.

## Отложено

| Механизм | Почему не нужен в MVP | Упрощение в MVP | Когда возвращаться |
|---|---|---|---|
| CAS-транзакция для локальных файлов, защита от конкурентной подмены каталогов, symlink/reparse races | Workspace считается доверенным и работает под контролем одного пользователя | Проверка хеша непосредственно перед записью, временный файл и атомарная замена | Несколько независимых writers или недоверенная общая файловая система |
| Собственный строгий parser unified diff и специальные случаи файлов без завершающего newline | Diff нужен для просмотра человеком, а не как внешний формат обмена | Стандартный `git diff`/`difflib`; approval привязывается к хешу кандидата | Появится импорт или применение patch сторонней системой |
| Расширенный quality gate из множества низкоуровневых правил | Повышает стоимость поддержки раньше появления реальных ошибок | Обязательные секции, отсутствие placeholder/секретов, источники для SLA, интеграций и endpoint, отсутствие конкретных сценариев/данных/протоколов | Статистика прогонов покажет повторяющийся класс дефектов |
| Selective refresh, source-to-section impact map и сравнение исторических manifest | Для первой версии полная пересборка проще и надёжнее | Повторный сбор всех подтверждённых источников. **Incremental resume** через `run-state.json` теперь поддерживается (шаг 7 gap approval итеративен, прерывания флоу не требуют restart). Selective refresh (пересборка только изменённых источников) остаётся отложенным. | Полная актуализация станет заметно долгой или дорогой |
| Обработка удаления модулей, смены kind, смешанных snapshot histories и dirty-state переходов | Это редкие изменения конфигурации workspace, которые пользователь всё равно подтверждает | Новое подтверждение workspace и полный повторный сбор | Появится регулярная автоматическая актуализация без участия пользователя |
| Полный golden workflow с несколькими временными Git-репозиториями и exhaustive filesystem-инвариантами | Не проверяет основную ценность быстрее простого E2E | Один локальный happy-path fixture и три обязательных отказа публикации | Перед production rollout или поддержкой нескольких платформ |
| Расширенное восстановление Confluence после `write-result-unknown`, управление labels/parent/title и поиск другой страницы | MVP публикует только в заранее подтверждённую страницу | Проверка page ID/version, обновление тела и простой receipt результата | Появятся реальные сбои сети после update или требования к структуре Confluence |

## Уже написанный экспериментальный код

Часть отложенных механизмов уже присутствует в feature-ветке как результат
исследования. Это не делает их частью MVP. Их не следует расширять или включать
в критерии приёмки. Удаление, обход или упрощение такого кода выполняется
отдельным контролируемым изменением после проверки зависимостей.

## Правило возврата из backlog

Механизм возвращается в план только при наличии наблюдаемой проблемы,
измеримого ограничения MVP или нового требования эксплуатации. Само наличие
экспериментальной реализации не является причиной включать механизм в MVP.
