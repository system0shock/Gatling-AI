# Дизайн: онбординг системы — каталог эндпоинтов и пейлоадов

Дата: 2026-06-11. Статус: решения зафиксированы из диалога, ожидает финального
ревью спеки перед планированием. Фазирование: **после Фазы 2** (фича «2.5» или
начало Фазы 3 — предусловие для `debug-with-sut`).

## Цель

Дать системе (SUT) постоянный слой переиспользуемых артефактов в репозитории
нагрузочного тестирования: паспорт системы, каталог запросов («ручек») и
сборник пейлоадов. При составлении нового сценария агент ориентируется на то,
что уже известно о системе, вместо повторного выяснения/выдумывания — это
экономит контекст (токены) и убирает дублирование описаний запросов между
сценариями. Сценарий вырождается в чистую бизнес-историю: какую ручку с каким
пейлоадом дёрнуть и откуда взять данные.

## Решения

### 1. Layout уровня системы

Продолжение ко-локации naming-and-layout — артефакты системы живут рядом с её
сценариями (репозиторий = реестр, внешних хранилищ нет):

```
scenarios/<SYSTEM>/
  system.yaml            # паспорт системы
  endpoints.yaml         # каталог сущностей запросов
  bodies/                # сборник пейлоадов (json/xml-шаблоны)
    checkout-single.json
    checkout-bulk.json
  <id>-<NNN>/            # сценарии, как сейчас
    scenario.yaml
    bodies/              # локальные одноразовые тела (escape hatch + миграция)
    ...
```

Коллизий с правилами layout нет: сценарии — директории по маске `<id>-<NNN>`,
артефакты системы — файлы и зарезервированная папка `bodies/`.

Фича также фиксирует до сих пор не закреплённую конвенцию репозитория
пользователя: `scenarios/` (источники правды) + Maven-проект Gatling рядом
(например `gatling/`), bootstrap обоих — задача онбординга.

### 2. `system.yaml` — паспорт системы

- `base_url` по средам (env-параметры, как сейчас в `sut`);
- пути к репозиториям кода SUT (лежат рядом, для FR5.1 / `debug-with-sut`);
- обвязка: Kafka (брокеры/топики по именам), БД (датасорсы), прокси;
  **только топология, никаких кредов** (NFR5);
- фиксация выбранного Kafka/JDBC-стека после спайка (дом для FR5.6.2).

### 3. `endpoints.yaml` — каталог сущностей запросов

Сущность («ручка») — то, что стабильно у системы:

```yaml
endpoints:
  checkout-submit:
    method: POST
    path: /checkout
    headers: { Content-Type: application/json }   # дефолты
    checks: [ { status: 200 } ]                   # базовый контракт
```

- **Источники наполнения:** импорт OpenAPI/swagger при онбординге
  (детерминированный тул `openapi_importer`) + пополнение из миграций
  (`convert-from-jmeter` дедуплицирует повторяющиеся семплеры; запросы,
  которых нет в спеке, помечаются `source: legacy`).
- **Защита контекста** (паттерн `jmx_parser --summary/--element`): каталог
  двухуровневый — компактный индекс (строка на ручку: method + path +
  однострочное summary) + срез по запросу с полной сущностью. Агент не читает
  сырой `swagger.json` и не тянет весь каталог в контекст.
- **Каталог — advisory, не источник истины:** спека SUT живёт своей жизнью;
  команда refresh показывает дифф с прошлого импорта; lint-сверка
  `method+path` сценариев с каталогом — warning, не blocking.

### 4. Ссылочная семантика (решение пользователя: вариант «ссылки», не copy)

Обоснование: на целевой системе одни и те же ручки используются во многих
скриптах с разными пейлоадами; запросы сущностно одни — правка в одном месте.

Шаг сценария ссылается на сущность и добавляет употребление:

```yaml
- name: submit-checkout
  transaction: "03 checkout.submit - Submit checkout"
  endpoint: checkout-submit                  # ссылка на сущность
  request:
    body_file: bodies/checkout-single.json   # пейлоад из общего сборника
    headers: { X-Flow: bulk }                # merge поверх дефолтов
  checks:
    - extract: { type: jsonPath, expr: "$.orderId", saveAs: orderId }
```

Правила (явные и скучные, без магии):

1. **Merge:** headers — merge с приоритетом сценария; body/body_file — только
   из сценария; checks — каталожные плюс сценарные (аддитивно, без замещения).
2. **Escape hatch:** полный `request` без `endpoint`-ссылки остаётся валидным
   (текущая форма). Существующие сценарии не требуют миграции; одноразовые
   запросы не обязаны попадать в каталог.
3. **Lint, генератор, рендерер работают по resolved-форме:** lint резолвит
   ссылку, проверяет существование сущности, применяет merge и гоняет
   существующие правила как обычно; генератор резолвит перед рендером Java.

### 5. Пейлоады: три слоя переиспользования

| Слой | Где живёт | Кто переиспользует |
|---|---|---|
| Ручка (method/path/дефолтные headers/базовый check) | `endpoints.yaml` | все сценарии системы |
| Пейлоад-шаблон (структура тела с `#{var}`) | `scenarios/<SYSTEM>/bodies/` | сценарии с этой структурой тела |
| Данные (значения переменных) | сценарий: фидеры/экстракции/env | только свой сценарий |

- Общий пейлоад = шаблон с плейсхолдерами; данные приходят из сессии.
  Структурно разные тела — разные пейлоады (не склеивать насильно).
- **Резолв `body_file` детерминированный:** сначала папка сценария, затем
  `scenarios/<SYSTEM>/bodies/` (точный механизм — порядок поиска или явный
  префикс — решается в плане). Lint обязан однозначно сказать, какой файл
  уедет в симуляцию.
- **Connectivity-проверка:** расширение correlation-lint — все плейсхолдеры
  используемого шаблона определены сценарием (фидер/extract/env), иначе
  blocking до компиляции.
- Пин старой версии тела для отдельного сценария: копия в локальный
  `bodies/` + явная ссылка (тот же escape hatch).
- Конвертер JMeter предлагает продвижение повторяющихся тел на уровень
  системы — с подтверждением и осмысленным kebab-case именем (общие файлы
  правятся руками, хэш-имена не годятся).

### 6. Видимость изменений (закрывает риск NFR6)

Ревью сценария не требует прыжков по файлам: `passport.md` рендерится по
resolved-форме (запрос в развёрнутом виде с пометкой «из каталога»).
Следствие — правка `endpoints.yaml` или общего пейлоада делает паспорта
зависимых сценариев устаревшими, а свежесть паспорта quality gate уже
проверяет: **молчаливое изменение чужих сценариев невозможно конструктивно**,
гейт перечисляет все затронутые сценарии.

### 7. Скилл `system-onboarding` (новый)

Диалоговый онбординг новой системы:

1. Вопросы: код системы (`system`), среды/base_url, пути к репо SUT,
   обвязка Kafka/БД → `system.yaml`.
2. Bootstrap layout: `scenarios/<SYSTEM>/` + Maven-проект (существующий
   генераторный bootstrap).
3. Импорт OpenAPI (`openapi_importer`) → `endpoints.yaml`; при отсутствии
   спеки — пустой каталог, наполнение из миграций/диалога.
4. `scenario-from-docs` и `convert-from-jmeter` дополняются шагом сверки с
   каталогом (предлагать ручки из каталога, фиксировать новые).

## Вне объёма (YAGNI)

- Дефолтный `body_file` у сущности в `endpoints.yaml` — старт **без
  дефолтов**, ссылка на пейлоад всегда явная в шаге (добавить позже дёшево,
  убрать больно). Открытый вопрос — пересмотреть по практике.
- Версионирование каталога (несколько версий одной ручки) — пин через
  локальную копию покрывает потребность.
- Переиспользуемые цепочки (`chains`) уровня системы — отдельное решение
  после реальных прогонов миграции (см. находки сверки с моделью Gatling).
- Автообновление каталога по расписанию/CI — только ручной refresh.
- Блокирующая сверка с каталогом — каталог advisory, источник истины для
  миграции — IR, для новых сценариев — требования.

## Принятые в диалоге решения (2026-06-11)

1. Семантика **ссылок** (вариант 2), а не copy-on-write: на основной системе
   пользователя одни ручки используются с разными пейлоадами; сущность —
   в каталоге, употребление — в сценарии.
2. Пейлоады — отдельный общий сборник `bodies/` на уровне системы
   (предложение пользователя): правим пейлоад, а не каждый запрос.
3. Три слоя переиспользования: ручка / пейлоад-шаблон / данные.
4. Merge-правила: headers merge (приоритет сценария), body только из
   сценария, checks аддитивно.
5. Escape hatch: полный `request` без ссылки валиден; локальные `bodies/`
   остаются.
6. Ревью по resolved-паспорту; видимость правок каталога — через устаревание
   паспортов и quality gate.
7. Фазирование: после Фазы 2, в скоуп Фазы 2 не входит.
