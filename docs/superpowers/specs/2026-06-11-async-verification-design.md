# Дизайн: верификация асинхронных событий (Kafka) — await и пост-проверка

Дата: 2026-06-11. Статус: черновик из диалога, ожидает финального ревью.
Предусловие: спайк Kafka/JDBC (последний шаг Фазы 2) — его скоуп уточняется
этим документом. Назначение: **новые скрипты и доводка мигрированных**;
сама миграция (Фаза 2) этой фичи не ждёт.

## Контекст и проблема (вход пользователя)

Kafka и Postgres критичны. HTTP-прокси умеет только **отправлять** в топики;
чтение сегодня — через БД пользователя (листнеры пишут в неё весь поток
топиков), причём не поллингом, а **одним JDBC-запросом на итерацию**:
«есть ли событие через X минут». Следствия:

- живых метрик задержек нет — только бинарный факт «дошло/не дошло за X»;
- лаг листнеров и БД подмешивается в результаты;
- БД перегружается во время тестов (эффект наблюдателя).

Факты: доступ генератора нагрузки к брокерам на чтение есть; корреляция —
по данным, которые скрипт сам генерирует и отправляет; retention топиков
~сутки; SLA проверяется **от шага, инициирующего отправку, до попадания
события в топик**; из БД скрипты не только проверяют, но и **читают данные
для дальнейших шагов**.

## Решения

### 1. Два механизма вместо чтения через БД

Решение пользователя: БД из Kafka-контура выводится (остаётся для отдельных
кейсов); проверка асинхронщины — двумя взаимодополняющими механизмами,
оба читают топики напрямую:

| Механизм | Когда | Что даёт |
|---|---|---|
| **`await`** (in-run) | результат нужен по ходу сценария; живые метрики | per-event лаг как транзакция в отчёте Gatling |
| **Reconciliation** (post-run) | массовая проверка доставки | % доставки + распределение лага по всему прогону, нулевой эффект наблюдателя |

### 2. `await`-шаг (in-run)

```yaml
- name: await-order-event
  transaction: "05 order.await-event - Await order event in topic"
  await:
    via: kafka
    topic: orders-out
    match: { key: "${orderId}" }      # корреляция по своим же данным
    since: submit-order               # SLA: лаг от старта шага-инициатора
    timeout_seconds: 30
    saveAs: orderEvent                # опционально: тело для следующих шагов
```

- **Механика:** один фоновый консьюмер на топик внутри симуляции (не
  по-VU!), in-memory корреляционная карта «ключ → сообщение»; шаг VU ждёт
  свой ключ с таймаутом. Деталь реализации (плагин galax-io requestReply
  или кастомный Action на kafka-clients) — по результату спайка.
- **Семантика измерения:** `since: <step-name>` — лаг считается от старта
  шага-инициатора отправки (зафиксированный SLA), а не от входа в await.
  Отдельная транзакция в отчёте: асинхронный лаг — самостоятельная метрика,
  не размазывается по HTTP-временам.
- Таймаут → KO транзакции (с штатной обработкой, сценарий продолжается
  или останавливается — настройка шага).

### 3. Reconciliation (post-run)

- Во время прогона шаги отправки пишут correlation id + таймстемп старта в
  лог прогона (файл рядом с отчётом, формат определит план).
- После прогона тул (`tools/kafka_reconcile`, новый) читает топик
  (retention ~сутки — позволяет), матчит по ключам и считает: % доставки,
  распределение лага (p50/p95/p99/max), список недоставленных id.
- Выход: `reconciliation-report.md/json` рядом с Gatling-отчётом;
  опциональная интеграция с quality gate (порог % доставки → warning).

### 4. JDBC: остаётся, но в другой роли

- **Read-for-use** — первоклассный шаг: запрос → `saveAs` → данные для
  следующих шагов. Минимальный блок `jdbc: {query, saveAs}` из спеки
  Фазы 2 оказывается правильной формой именно для этого кейса; реализация —
  кастомный action (HikariCP + драйвер PG) из спайка.
- Проверка Kafka-событий через БД — **не целевой путь**; `await via: jdbc`
  (полл с interval/timeout) — опционально, низкий приоритет, только для
  кейсов, где топик недоступен.

### 5. Связь с миграцией (Фаза 2)

Миграция конвертирует легаси-паттерны **как есть**, помечая кандидатов на
апгрейд тегами (теги шагов уже в спеке Фазы 2):

| Легаси-паттерн | Конвертация | Тег |
|---|---|---|
| отправка через HTTP-прокси | HTTP-шаг | `kafka-via-proxy` (уже в спеке) |
| `pause X` + JDBC-проверка «есть ли событие» | pause + jdbc-шаг (заглушка до спайка) | `async-check-via-db` (новый) |

После реализации фичи — upgrade-проход по тегам: замена db-проверок на
`await`/reconciliation. Конвертер ничего «умного» сам не переделывает.

### 6. Уточнение скоупа спайка (конец Фазы 2)

Приоритеты инвертируются относительно §9 спеки Фазы 2 (там фокус на
producer-плагине): produce уже решён прокси, критичная неизвестная —
**consume**. Спайк обязан доказать:

1. фоновый консьюмер + корреляционная карта + per-event лаг (основа await);
2. чтение топика пост-фактум для reconciliation (объёмы прогона за сутки);
3. JDBC one-shot action (HikariCP + PG) для read-for-use.

Нативный produce — stretch goal (зависит от открытого вопроса о прокси).

## Вне объёма (YAGNI)

- Нативный Kafka-produce — прокси работает; пересмотр после ответа на
  открытый вопрос №1.
- `await via: jdbc` (поллинг БД) — только если всплывёт кейс без доступа
  к топику.
- Автовыгрузка датасетов из БД перед тестом — отдельная давняя хотелка,
  не сюда.

## Открытые вопросы

1. Прокси в SLA-пути: он продакшен-репрезентативен (приложения тоже
   публикуют через него) или тестовый костыль? Влияет на честность метрики
   send→topic и на судьбу нативного produce.
2. Формат `match` по факту парка: ключ сообщения, header или поле тела?
   (Корреляция «по своим данным» допускает все три.)
3. Где и в каком формате хранить correlation-лог прогона для reconcile.
