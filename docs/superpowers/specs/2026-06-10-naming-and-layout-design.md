# Дизайн: конвенции именования и структура папок сценариев

Дата: 2026-06-10. Статус: утверждён пользователем (диалог), ожидает ревью спеки.

## Цель

Зафиксировать правила именования скриптов (симуляций), транзакций, фидеров и
структуру папок так, чтобы они выводились из одного источника правды
(`scenario.yaml`) и проверялись автоматически (lint / quality gate), а не
поддерживались руками в нескольких местах.

## Решения

### 1. Поля в YAML — источник правды

В объект `scenario` добавляются два обязательных поля:

| Поле | Формат | Пример | Смысл |
|---|---|---|---|
| `system` | `^[A-Z][A-Z0-9]{1,9}$` | `SHOP` | Код системы (SUT) |
| `number` | целое ≥ 1; уникально в рамках `system` | `1` | Номер скрипта |

`id` остаётся kebab-case именем сценария **без** системы и номера
(`checkout-mix`). Производный **скрипт-реф** строится инструментами по маске
пользователя `ПрефиксСистемы_НаименованиеСценария_НомерСкрипта`:

```
<SYSTEM>_<PascalCase(id)>_<NNN>   →   SHOP_CheckoutMix_001
```

`NNN` — номер с ведущими нулями до 3 знаков (при number > 999 — без
усечения, 4+ знака). Скрипт-реф нигде не пишется руками — его порождает
генератор и сверяет lint.

**Откуда берутся значения.** `SHOP`/`CheckoutMix` в этом документе — только
примеры. Фактические `system`, `id` и `number` агент НЕ выдумывает: они
выясняются у пользователя в диалоге `scenario-from-docs` (новые пункты
чек-листа извлечения сущностей). Допустимо предложить значение как
заготовку — например, следующий свободный `number` по скану `scenarios/` или
`id` из названия файла требований, — но только как вопрос с подтверждением.
После подтверждения модель ориентируется по этим значениям во всех
производных именах.

### 2. Имя Java-класса симуляции

Класс симуляции = скрипт-реф как есть: `SHOP_CheckoutMix_001`. Суффикс
`Simulation` упраздняется (в репозитории нагрузочных тестов всё — симуляции;
подчёркивания в Java легальны). Это имя видно в Jenkins, отчётах Gatling и в
`-Dgatling.simulationClass`.

### 3. Структура папок — ко-локация

```
scenarios/
  <SYSTEM>/                      # папка системы, имя = scenario.system
    <id>-<NNN>/                  # папка сценария, напр. checkout-mix-001/
      scenario.yaml              # источник правды (фиксированное имя)
      passport.md                # рендер-паспорт (фиксированное имя)
      <feeder-name>.csv          # фидеры рядом со сценарием
      mock.routes.json           # опционально: конфиг mock-SUT для smoke
```

- Один сценарий = одна папка: атомарные PR, нет сирот при удалении.
- Renderer по умолчанию пишет `passport.md` рядом со сценарием.
- Quality gate по умолчанию сверяет свежесть `passport.md` в папке сценария
  (`--docs-dir` остаётся как явный override). Это устраняет ложный
  `renderer.docs-stale` для сценариев вне `examples/` (находка E2E-приёмки).
- Уникальность пары `(system, number)` проверяется сканом дерева `scenarios/`
  (репозиторий = реестр; внешний реестр не нужен). Проверка живёт в lint как
  отдельный repo-режим и вызывается из quality gate.

### 4. Фидеры

- Имя фидера: существительное во множественном числе, kebab-case
  (`terms`, `users`).
- Имя файла: строго `<имя-фидера>.csv`, лежит в папке сценария.
- Оба правила переходят из рекомендации в доке в blocking-проверки lint.
- Исправление золотого примера: термины поиска переезжают из `products.csv`
  в `terms.csv`.

### 5. Транзакции

Маска не меняется: `<NN> <domain>.<action> - <Title>` (regex, уникальность,
≤80 символов, запрет секретов/имён сред — уже в lint). Новое правило:
нумерация `NN` **сквозная по всей симуляции** (через все популяции), повтор
`NN` — blocking-находка. Золотой пример приводится в соответствие
(сейчас `background-search` начинает нумерацию заново с `01`).

## Объём изменений

| Компонент | Изменение |
|---|---|
| `schemas/scenario.schema.json` | `system`, `number` — обязательные поля (breaking; проект pre-1.0, миграция только своих примеров) |
| `tools/scenario_lint` | правила: формат `system`/`number`; repo-режим — уникальность `(system, number)` и соответствие пути папки `scenarios/<system>/<id>-<NNN>/` полям YAML; фидер-файл = имя фидера; сквозной `NN` |
| `tools/gatling_generator` | имя класса = скрипт-реф (без суффикса `Simulation`) |
| `tools/scenario_renderer` | дефолтный вывод `passport.md` рядом со сценарием |
| `tools/quality_gate` | дефолтный поиск доки в папке сценария; вызов repo-проверки уникальности |
| `examples/scenarios/*` | перенос в `scenarios/<SYSTEM>/<id>-<NNN>/`, переименование фидеров, сквозная нумерация транзакций |
| `docs/SCENARIO_FORMAT.md` | новые правила именования и структуры |
| `skills/scenario-from-docs`, `skills/scenario-to-gatling` | обновление текстов процесса (куда писать YAML/доку, как зовётся класс); в чек-лист scenario-from-docs добавляются `system`/`id`/`number` как сущности, выясняемые у пользователя |

## Вне объёма (YAGNI)

- Внешний реестр номеров (Confluence/Jira) — репозитория достаточно.
- Глобальная (межсистемная) уникальность номеров — отклонено пользователем.
- Автовыдача следующего свободного номера инструментом — можно добавить
  позже как подсказку lint, в этот объём не входит.

## Принятые в диалоге решения

1. Номер уникален **в рамках системы**, реестр — сам репозиторий.
2. Java-класс — **маска как есть**, без суффикса `Simulation`.
3. Дока хранится **рядом со сценарием** (ко-локация), предложение пользователя.
4. Дизайн из 5 секций утверждён целиком 2026-06-10.
5. `system`/`id`/`number` — значения от пользователя (диалог scenario-from-docs),
   агент не выдумывает их сам; SHOP/CheckoutMix в спеке — только примеры.
