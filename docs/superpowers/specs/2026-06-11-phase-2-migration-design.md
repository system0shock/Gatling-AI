# Дизайн: Фаза 2 — миграция JMeter → Gatling

Дата: 2026-06-11. Статус: утверждён пользователем (диалог), ожидает ревью спеки.

## Цель

Дать рабочий конвейер миграции легаси-скриптов JMeter: `.jmx` → паспорт →
`scenario.yaml` → Java-симуляция, с переиспользованием контура Фазы 1
(схема, lint, рендерер, генератор, quality gate) и явными human-in-the-loop
гейтами. Скрипты в парке без документации (или с доками в Confluence),
содержат плагинные тред-группы, сложные бизнес-процессы и JSR223-логику;
файлы достигают 100–200 МБ за счёт тел запросов.

## Зафиксированные решения диалога

| Вопрос | Решение |
|---|---|
| Скоуп фазы | Оба скилла (`document-legacy-jmeter`, `convert-from-jmeter`), HTTP-first; Kafka/JDBC-шаги — заглушки с TODO (FR5.6.3), спайк протоколов — последним шагом фазы |
| Тест-данные | Гибрид: синтетические golden `.jmx` в репо для тестов; реальные скрипты пользователь прогоняет локально вне репо, обратная связь через conversion-report |
| JSR223 | Два прохода: автопроход переводит типовые паттерны, сложные блоки → структурированные TODO; затем явный второй проход — агент переводит по одному блоку с ревью оригинал/перевод. Переводит всегда агент, человек ревьюит |
| Confluence | Чтение страниц через штатный Atlassian MCP уже в Фазе 2 (fallback — экспорт файлом, MCP в дев-репо недоступен); публикация — Фаза 3 |
| Архитектура | Вариант A: детерминированный парсер + агент поверх IR (см. ниже); прямой jmx→Java и «агент читает XML сам» отклонены |

Факты о парке (вход от пользователя): тред-группы чаще плагинные
(jp@gc Ultimate, Stepping, Concurrency, Arrival), обычно одна TG = весь
бизнес-процесс, но бывают этапные сценарии (первые 20 минут — запросы А,
затем Б) с передачей данных между группами через props/очереди — такие
случаи требуют максимума гейтов. Транзакции есть всегда, часто Module
Controller. JSR223 — в основном pre/post-процессоры (подготовка/обработка
данных), 90% скриптов — бэкенд. Экстракторы regex/jsonPath, датасеты в CSV,
User Defined Variables хранят env-конфигурацию (хосты, порты, параметры
запуска). Kafka сейчас ходит через внешний HTTP-прокси (HTTP-запрос с телом
сообщения и топиком); JDBC редок. Скриптов на десятки семплеров, файлы
100–200 МБ из-за inline-тел.

## Решения

### 1. Поток данных и гейты

```
.jmx (+CSV/properties, до 200 МБ)
        |
        v
[ jmx_parser (Python, потоковый) ]            ← детерминированный тул
        |--> ir.json            (компактное дерево плана)
        |--> bodies/*           (вынесенные тела запросов)
        |--> jsr223/*.groovy    (извлечённые скрипты + классификация)
        |--> inventory.md       (нашли / не поддержано / флаги сложности)
        |
        v
   ГЕЙТ 1: ревью inventory  ← масштаб и сложность видны ДО работы агента
        |
        v
[ skill: document-legacy-jmeter ]             ← агент работает с IR, не с XML
        |
        v
   ГЕЙТ 2: ревью паспорта   ← «бизнес-логика понята верно?»
        |
        v
[ skill: convert-from-jmeter ]  проход 1 → scenario.yaml + conversion-report.md
        |
        v
   ГЕЙТ 3: scenario-lint + ревью YAML и отчёта
        |
        v
   проход 2 (JSR223-доводка): по одному блоку с ревью     ← ГЕЙТ 4
        |
        v
[ существующий scenario-to-gatling ] → Java-симуляция
        |
        v
   ГЕЙТ 5: существующий quality gate (compile, smoke, validator)
```

Принципы:

- **Агент никогда не читает `.jmx` напрямую** — только артефакты парсера
  (и 200 МБ не влезут в контекст, и нужен детерминизм).
- **Скрипты с флагами сложности** (этапные TG с передачей данных,
  нераспознанные плагины, JSR223 Sampler) идут по «внимательному» пути:
  обязательные остановки на каждом гейте. Простые скрипты могут проходить
  гейты 2–3 одним подтверждением.
- **Паспорт — обязательная ступень перед конвертацией**, но
  `document-legacy-jmeter` запускается и автономно (фича 3 PRD: только
  документация).
- Kafka-через-прокси конвертируется как HTTP-шаги с тегом `kafka-via-proxy`
  (метка для будущего апгрейда на нативную Kafka после спайка).

### 2. `jmx_parser` и формат IR

`tools/jmx_parser/` — единственное место чтения XML. Потоковый разбор
(`iterparse`): память ограничена независимо от размера файла, цель —
200 МБ за минуты; тела запросов в память целиком не поднимаются.

Артефакты:

1. **`ir.json`** — дерево: тред-группы → контроллеры → семплеры, с
   атрибутами для паспорта и конвертации. Формат версионируется и
   валидируется схемой `schemas/jmx-ir.schema.json` — контракт между
   парсером и скиллами.
2. **`bodies/`** — тела крупнее порога (~1 КБ) выносятся в файлы;
   одинаковые дедуплицируются по хэшу. В IR — ссылка, длина, превью.
3. **`jsr223/*.groovy`** — каждый блок отдельным файлом. В IR — метаданные:
   расположение (pre/post/sampler), родительский семплер, читаемые/
   записываемые переменные (эвристика `vars.get/put`, `props.get/put`),
   классификация **typical** (UUID/timestamp/random, сборка строк/JSON из
   переменных, простые условия) или **complex** (всё остальное; любое
   использование `props` — автоматически complex).
4. **`inventory.md`** — отчёт Гейта 1: счётчики по типам элементов, таблица
   supported/partial/unsupported, флаги сложности, статистика размеров.

**Покрытие элементов (supported в IR):**

| Категория | Элементы |
|---|---|
| Тред-группы | стандартная, jp@gc Ultimate / Stepping / Concurrency / Arrival → нормализация в профиль нагрузки |
| Контроллеры | Transaction, Module (с резолвом ссылки), If, Loop, Once Only, Throughput, Test Fragment |
| Семплеры | HTTP Request, JSR223 Sampler; JDBC Request распознаётся → TODO-заглушка |
| Конфиг | CSV Data Set, HTTP Defaults, Header/Cookie Manager, User Defined Variables → env-параметры, Counter, Random Variable |
| Экстракторы | Regex, JSON Path, Boundary |
| Assertions | Response, JSON, Duration |
| Таймеры | Constant, Uniform/Gaussian Random, Constant Throughput |

Нераспознанные узлы попадают в IR как `unsupported` (тип + путь в дереве) —
парсер обязан учесть каждый узел, silent drop исключён конструктивно.
Выключенные (`enabled="false"`) фиксируются как skipped.

**Граф связей (variable cross-reference):**

- у каждого элемента — `vars_produced` (saveAs, колонки CSV,
  Counter/Random Variable, `vars.put`) и `vars_consumed` (`${var}` в
  URL/теле/заголовках/параметрах, `vars.get`);
- глобальный `variable_index`: переменная → производители/потребители (id
  элементов); автоматические находки: «переменная без производителя»
  (разрыв корреляции; перед репортом проверяется на JMeter-функцию и props)
  и «производитель без потребителя» (мёртвая корреляция);
- структурные связи: Module Controller → фрагмент, транзакция → семплеры;
  `props` в индексе связывают тред-группы → подкрепляет флаг этапности.

Назначение двойное: паспорт пишется от потоков данных (имена транзакций в
легаси неинформативны), `correlation-lint` получает готовые данные, агент
предлагает имена по маске `<NN> domain.action - title` с фиксацией маппинга
«оригинал → новое» в conversion-report (FR5.8.5). Оригинальные имена в IR
сохраняются всегда.

**Защита контекста агента** (ограничение из диалога): полный граф живёт в
`ir.json`; агенту в контекст попадают только курируемые срезы — в
`inventory.md` лишь находки, не вся матрица; CLI-режимы парсера
(`--summary`, `--element <id>`) выдают срез по запросу. Скиллы предписывают
агенту работать с inventory/паспортом/срезами; прямое чтение `ir.json` и
`.jmx` запрещено инструкцией скилла; тела — только превью.

**Флаги сложности** (поднимаются на Гейт 1): несколько TG со сдвигами по
времени, использование `props`/межпоточных очередей, нерезолвящийся Module
Controller, неизвестные плагины, JSR223 Sampler.

### 3. Layout миграции

Продолжение ко-локации naming-and-layout; миграционные артефакты — в
подпапке `migration/`:

```
scenarios/<SYSTEM>/<id>-<NNN>/
  scenario.yaml
  passport.md              ← единый паспорт (для миграции расширенный)
  <feeder-name>.csv        ← скопированы из легаси
  bodies/                  ← вынесенные тела (body_file ссылается сюда)
  snippets/                ← Java-сниппеты переведённых JSR223
  migration/
    ir.json
    inventory.md
    conversion-report.md
    jsr223/*.groovy        ← оригиналы, трассируемость
```

`system`/`id`/`number` скилл спрашивает у пользователя (never invent).
Исходный `.jmx` остаётся вне репо, путь задаёт пользователь.

### 4. Расширения `scenario.schema.json` (+ lint, генератор, рендерер)

1. **`body_file`** — альтернатива `body` в request (взаимоисключающие);
   lint проверяет существование файла; генератор → `ElFileBody`/`RawFileBody`.
2. **`profile: stages`** — список ступеней: closed-ступень
   `{users, ramp_seconds, hold_seconds}`, open-ступень
   `{users_per_second, ramp_seconds, hold_seconds}`. Нормализует Ultimate
   (произвольный график), Stepping (генерится в ступени), Concurrency
   (ramp+hold), Arrival (open). Маппинг «параметры TG → ступени» — в
   conversion-report.
3. **`start_after_seconds`** у population (→ `nothingFor`) — простая
   этапность «20 минут А, потом Б». Этапность с передачей данных между
   группами этим не решается — остаётся complex-флагом и TODO.
4. **`hooks.before` / `hooks.after`** у шага — escape hatch для JSR223:

   ```yaml
   hooks:
     before:
       - ref: migration/jsr223/sign-request.groovy   # оригинал
         kind: translated | todo
         snippet: snippets/SignRequest.java           # обязателен при translated
         summary: "подписывает тело ключом из фидера"
         reads: [user, key]
         writes: [signature]
   ```

   Генератор: `translated` → подключение сниппета (`exec(session -> ...)`),
   `todo` → TODO-комментарий с summary и путём к оригиналу. Lint: при
   `translated` сниппет существует. Количество `todo` идёт в отчёт гейта
   как `manual_review_required` (не blocking: код компилируется и
   запускается, но статус — `passed_with_warnings`, не чистый passed).
5. **`protocol: kafka | jdbc`** в enum с минимальными блоками
   (`kafka: {topic, key, payload}`, `jdbc: {query, saveAs}`); генератор
   выдаёт заглушку с TODO (FR5.6.3) до результатов спайка.
6. **`tags`** у шага (список строк) — маркер `kafka-via-proxy` и будущие
   метки.

**Сознательно не расширяем (YAGNI):** If/While/Loop/Once Only/Throughput
в YAML не представляются — они есть в IR и паспорте, при конвертации дают
`partial` + TODO-хук с описанием семантики. По вводу пользователя они
редки; если реальные прогоны покажут обратное — отдельная итерация.

### 5. Скилл `document-legacy-jmeter`

- **Вход:** путь к `.jmx` (+ CSV/properties); опционально — ссылка на
  Confluence и/или путь к репо SUT.
- **Шаг 1.** Запуск `jmx_parser`, показ `inventory.md` — Гейт 1. При флагах
  сложности скилл явно объявляет «внимательный путь, авто-прохода не будет».
- **Шаг 2.** Ссылка на Confluence → чтение через Atlassian MCP; при
  недоступности MCP — экспорт файлом от пользователя. Контент — контекст,
  **источник истины — IR**: расхождения «доки говорят X, скрипт делает Y»
  фиксируются отдельной секцией паспорта, не разрешаются молча.
- **Шаг 3.** Паспорт по единому шаблону (стиль паспорта сценария + легаси-
  секции): назначение и бизнес-процесс; таблица транзакций (оригинал →
  предлагаемое имя по маске); потоки данных по шагам (срезы
  `variable_index`); таблица JSR223 (что делает, читает/пишет,
  typical/complex); профиль нагрузки словами; env-конфигурация из UDV;
  зависимости (CSV, properties, прокси-Kafka); расхождения с Confluence;
  неподдержанные элементы. Неоднозначность бизнес-смысла → вопрос
  пользователю, не догадка (FR1.4).
- **Выход:** `passport.md` — Гейт 2. Скилл самодостаточен (фича 3 PRD);
  публикация в Confluence — Фаза 3.

### 6. Скилл `convert-from-jmeter`

- **Предусловие:** утверждённый паспорт (без него — направление в
  `document-legacy-jmeter`).
- **Шаг 0.** Вопрос `system`/`id`/`number`, создание папки по layout.
- **Проход 1 (типовое):** populations из TG (профили → `stages` по таблице
  маппинга), шаги из семплеров, checks из assertions+экстракторов, фидеры
  из CSV, env из UDV, тела → `body_file`, kafka-via-proxy → HTTP+тег,
  JDBC → заглушка. JSR223: typical → Java-сниппеты сразу, complex →
  `hooks` с `kind: todo`. Выход — `scenario.yaml` + `conversion-report.md`:
  полная таблица диспозиции каждого элемента
  (converted/partial/todo/skipped-disabled), маппинг имён, маппинг
  профилей. **Сумма диспозиций обязана сойтись с inventory** — защита от
  потерь и метрика M2 (≥80% auto).
- **Гейт 3:** `scenario-lint` + ревью YAML и отчёта.
- **Проход 2 (доводка):** по каждому `todo`-хуку: оригинал Groovy +
  контекст (vars in/out, описание из паспорта) → предложенный перевод →
  пользователь утверждает/правит → сниппет сохраняется, `kind` →
  `translated`, отчёт обновляется. Остановка на любом блоке допустима —
  остальные остаются явными TODO.
- **Финал:** передача существующему `scenario-to-gatling` (bootstrap,
  генерация, компиляция, smoke, quality gate). Гейт расширяется проверкой:
  оставшиеся `todo`-хуки → `manual_review_required`,
  статус `passed_with_warnings`.

### 7. Ошибки и краевые случаи

- **Битый `.jmx`** (кривой XML, кодировка): парсер падает с диагностикой;
  частичный IR не пишется — либо полный разбор, либо явная ошибка.
- **JMeter-функции** (`${__UUID}`, `${__time}`, `${__Random}`,
  `${__P(...)}`): стандартные распознаются; `__UUID/__Random/__time` —
  типовые переводы, `__P` → env-параметры, неизвестные → todo-хук.
  «Переменная без производителя» сперва проверяется на функцию/props.
- **Нерезолвящийся Module Controller, отсутствующий CSV** — блокирующие
  вопросы на Гейте 1 / finding'и lint, не предположения.
- **Идемпотентность (NFR6):** при существующих артефактах конвертер не
  перезаписывает молча — показывает, что изменится, и просит
  подтверждение; ручные правки (scenario.yaml после Гейта 3, snippets/)
  регенерация не трогает без явного согласия.
- **Сходимость диспозиции:** элементы inventory = сумма
  converted+partial+todo+skipped в conversion-report; проверяется тестом и
  гейтом.

### 8. Тестирование

- Юнит-тесты на каждый тул (pytest, культура репо): фикстуры-фрагменты
  `.jmx` по типам элементов, тесты IR-схемы, `variable_index`,
  классификатора JSR223, нормализации профилей TG → stages.
- **Два golden `.jmx`** в `examples/jmx/`:
  1) *простой бэкенд* — одна Ultimate-TG, транзакции, regex/jsonPath, CSV,
     UDV, типовые JSR223, крупное тело → полный путь до `gate passed`
     (smoke на mock);
  2) *сложный этапный* — две TG со сдвигом, передача через props, complex
     JSR223, kafka-via-proxy, JDBC-семплер → ожидаемые флаги сложности,
     конвертация с TODO, `passed_with_warnings`.
- **Перфоманс-тест парсера:** генератор раздувает golden до ~150 МБ телами;
  проверка ограниченной памяти и времени в минутах (помечен slow).
- Реальные скрипты — локально у пользователя (гибрид), обратная связь через
  conversion-report.

### 9. Спайк Kafka/JDBC (последний шаг фазы)

- **Kafka:** проверить galax-io gatling-kafka-plugin на 3.12 + Java DSL;
  при провале — кастомный Action на kafka-clients.
- **JDBC:** кастомный action (HikariCP + драйвер PostgreSQL).
- Результат: spike-отчёт в `docs/` + либо рабочая генерация
  `kafka`/`jdbc`-шагов, либо обоснованное «остаётся заглушкой».
- Перевод прокси-Kafka на нативную — отдельная работа после спайка (шаги
  уже помечены тегом `kafka-via-proxy`).

### 10. Критерии приёмки фазы

- Оба golden проходят свои пути с ожидаемыми статусами гейта.
- Диспозиция элементов сходится на 100% (silent drop отсутствует).
- Простой golden: ≥80% элементов auto-converted (метрика M2).
- Парсер держит ~150 МБ в рамках бюджета памяти/времени.
- Все тестовые сьюты зелёные.
- Прогон на реальном скрипте пользователя: паспорт подтверждён,
  conversion-report осмыслен.

## Вне скоупа фазы (зафиксировано на будущее)

- Публикация паспортов в Confluence через MCP — Фаза 3.
- Нативная Kafka-миграция прокси-шагов — после спайка.
- Автовыгрузка датасетов из БД перед тестом вместо статических CSV —
  упомянуто пользователем как желаемое будущее, в Фазу 2 не входит.
- If/While/Loop/Once Only/Throughput-конструкции в YAML — по результатам
  реальных прогонов.
- Перевод JSR223 без ревью (полный авто-проход) — осознанно не делаем.
